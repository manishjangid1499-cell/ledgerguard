# LedgerGuard Failure Model & Mitigation Strategy

This document details potential failure scenarios in distributed financial systems, the theoretical risks they introduce, the required system behavior to preserve correctness, and the corresponding implementation phase in the build plan.

---

## Failure Matrix

| # | Failure Scenario | What Can Go Wrong | Expected System Behavior | Addressed In |
|---|------------------|-------------------|--------------------------|--------------|
| **1** | **Duplicate API Request** | Client retries `POST /transfers` or `POST /payments` due to client-side network glitch, causing double debits. | The idempotency engine matches `(client_id, idempotency_key)`, verifies SHA-256 request fingerprint, and returns the cached result without executing financial side effects. | **Phase 9** *(Idempotency)* |
| **2** | **Concurrent Spending (Double-Spend)** | Two simultaneous transfer requests exceed available balance when executed concurrently in separate threads. | Deterministic row-level locking (`PESSIMISTIC_WRITE` on `ledger_balance_snapshots` ordered by `ledger_account_id ASC`) serializes balance checks and updates; the second transaction observes the updated locked balance, detects insufficient funds, and throws `InsufficientFundsException`. The transaction rolls back cleanly (0 transfers, 0 journals, uncommitted idempotency claim dropped), leaving the idempotency key unpoisoned for safe retry after future funding. | **Phase 10 & 11** *(Transfers, Concurrency & Overdraft Prevention)* |
| **3** | **Deadlock Risk in Opposing Transfers** | Thread A transfers from Account 1 to Account 2 while Thread B transfers from Account 2 to Account 1 simultaneously. | Accounts are locked in a deterministic global order (`ORDER BY ledger_account_id ASC`) regardless of transfer direction, eliminating circular-wait conditions for touched accounts. Transient database exceptions propagate to caller as clean rollbacks without hidden automatic retry loops; callers can safely retry idempotent requests. | **Phase 11** *(Deterministic Locking)* |
| **4** | **Application Crash Before DB Commit** | Server process crashes or loses power mid-transfer execution before PostgreSQL transaction commit. | PostgreSQL rolls back all uncommitted changes; no partial ledger entries, balances, or outbox records exist. System state remains strictly consistent. | **Phase 7 & 10** *(ACID Posting & Transfers)* |
| **5** | **Application Crash After DB Commit** | Transaction commits in PostgreSQL, but server crashes before returning HTTP 200 to client. | Financial state and outbox events are already committed. When the client retries with the same `Idempotency-Key`, the system retrieves the committed result and returns it. | **Phase 9 & 16** *(Idempotency & Outbox)* |
| **6** | **Lost HTTP Response** | Transaction completes successfully, but network drop prevents client from receiving HTTP response. | Client retries with identical `Idempotency-Key`. The idempotency layer recognizes the completed transaction and returns the original response without re-executing. | **Phase 9** *(Idempotency)* |
| **7** | **Kafka Unavailable** | Kafka cluster is temporarily unreachable when financial transactions occur. | Financial transactions commit successfully to PostgreSQL along with pending outbox events. Outbox publisher retries delivery with exponential backoff until Kafka recovers. | **Phase 16 & 17** *(Transactional Outbox & Kafka)* |
| **8** | **Outbox Publisher Crash** | Outbox publisher process crashes mid-poll or mid-publish to Kafka. | Events remain in `PENDING` state with lease timestamps. Another instance or restarted publisher claims them via `SKIP LOCKED` and resumes publishing. | **Phase 17** *(Outbox Publisher)* |
| **9** | **Kafka Duplicate Delivery** | Kafka at-least-once delivery semantics cause the same event message to be delivered twice to workers. | The consumer's inbox deduplication mechanism (`processed_events` table) detects duplicate event ID within the consumer database transaction and ignores it. | **Phase 18** *(Notification Worker Inbox)* |
| **10** | **Consumer Crash / Redelivery** | Notification worker crashes after processing business effect but before committing Kafka offset. | On restart, Kafka redelivers the message; the consumer's inbox table recognizes the `event_id` as already processed and skips duplicate side effects. | **Phase 18** *(Inbox Deduplication)* |
| **11** | **PSP Failure Before Processing** | External PSP returns HTTP 500 or network error before processing deposit or withdrawal. | Transaction transitions to `FAILED`; any active balance holds are immediately released. No journal entries are posted. | **Phase 19, 20 & 21** *(PSP Integration & Holds)* |
| **12** | **PSP Timeout Before Processing** | Call to PSP times out before the PSP receives or processes the request. | Transaction transitions to `UNKNOWN` or `PROCESSING`. System initiates provider status query or awaits webhook before declaring state. Funds remain held. | **Phase 23** *(Ambiguous Outcomes)* |
| **13** | **PSP Timeout After Successful Processing** | PSP successfully commits payment/payout, but HTTP response times out on the return path. | Transaction is marked `UNKNOWN` / `RECONCILIATION_REQUIRED`. Funds are not prematurely refunded. Status poller or reconciliation syncs state with PSP. | **Phase 23 & 24** *(Lifecycle & Reconciliation)* |
| **14** | **Delayed Response from PSP** | PSP takes several minutes to process an asynchronous settlement. | Transaction stays in `PROCESSING` with active balance hold. Funds cannot be spent elsewhere until final webhook or reconciliation callback arrives. | **Phase 15 & 23** *(Holds & State Machines)* |
| **15** | **Delayed Webhook Arrival** | PSP webhook arrives hours or days after the initial transaction request. | Webhook processing verifies signature and updates operation state; if already resolved via polling, the webhook is recognized as redundant and safely acknowledged. | **Phase 22 & 23** *(Webhooks & State Machines)* |
| **16** | **Duplicate Webhook Delivery** | PSP sends the same webhook payload multiple times. | Webhook signature is validated and inbound `provider_events` table enforces unique constraint on `(provider_id, provider_event_id)`. Duplicates are acknowledged without action. | **Phase 22** *(Webhook Deduplication)* |
| **17** | **Out-of-Order Webhook Delivery** | Webhook for `SUCCEEDED` arrives before initial `CREATED` notification or vice versa. | State machine enforces legal state transitions (`CREATED` $\to$ `PROCESSING` $\to$ `SUCCEEDED`). Out-of-order transitions are evaluated against current state and applied safely. | **Phase 22 & 23** *(State Machine Guards)* |
| **18** | **Stale Provider State Update** | An outdated status callback arrives after an operation was already marked `RESOLVED` or `SUCCEEDED`. | Terminal states (`SUCCEEDED`, `FAILED`, `REFUNDED`) are immutable. The stale update is logged and rejected by the state machine validator. | **Phase 23** *(State Transitions)* |
| **19** | **Payment Insufficient Funds** | Customer attempts payment where available balance < gross amount. | Validated against locked customer snapshot before journal posting; transaction rolls back cleanly. No `Payment` row is committed, no journal entries exist, and the uncommitted idempotency slot is dropped, allowing safe retry with the same key after wallet funding. | **Phase 13** *(Merchant Payments)* |
| **20** | **Payment Fee Account Ambiguity / Misconfiguration** | Payment with fee > 0 encounters missing, multiple, or closed `PLATFORM_FEES` accounts. | Throws `PlatformFeeAccountException`; the entire transaction rolls back cleanly. No payment or journal committed; no silent loss or arbitrary fee account selection. | **Phase 13** *(Merchant Payments)* |
| **21** | **Payment Snapshot Arithmetic Overflow** | Posting payment causes account balance to exceed signed 64-bit integer limit. | PostgreSQL trigger detects arithmetic overflow and raises exception; transaction rolls back completely. 0 payment rows, 0 journals, 0 committed idempotency records. | **Phase 8 & 13** *(Balance Snapshots & Payments)* |
| **22** | **Concurrent Refund Requests & Over-Refunds** | Multiple simultaneous refund requests attempt to refund more than the original payment amount. | Parent `Payment` row is locked `FOR UPDATE` before cumulative refund calculation. Application and DB trigger enforce $\sum \text{Refunds} \le \text{grossAmountMinor}$. Requests exceeding the cap fail with HTTP 409 `REFUND_LIMIT_EXCEEDED` and roll back cleanly (0 refund rows, 0 journals, uncommitted idempotency slot dropped for safe retry). | **Phase 14** *(Refunds & Concurrency Control)* |
| **23** | **Refund on Non-SUCCEEDED or Unowned Payment** | Client attempts to refund an unowned, missing, `CREATED`, `PROCESSING`, or `FAILED` payment. | Unowned or non-existent payments return HTTP 404 (IDOR / anti-enumeration protection). Non-succeeded payments fail with HTTP 409 `PAYMENT_NOT_REFUNDABLE` and DB trigger enforces `payment.status = 'SUCCEEDED'`. Entire transaction rolls back cleanly. | **Phase 14** *(Refunds & Integrity)* |
| **24** | **Refund Fee Account Resolution / Journal Integrity Failure** | Original payment journal has missing, ambiguous, or multiple platform fee credit entries. | Throws `PlatformFeeAccountException` causing immediate rollback. Does not guess or fallback to current repository fee accounts; original immutable journal determines exact fee reversal. | **Phase 14** *(Refunds & Accounting Integrity)* |
| **25** | **Refund Balance Snapshot Overflow** | Compensating customer credit causes customer snapshot balance to exceed signed 64-bit integer range. | Trigger `trg_journal_transactions_update_snapshots` detects overflow and raises exception; transaction rolls back completely (0 refund rows, 0 journals, 0 committed idempotency records, unmutated balances). | **Phase 8 & 14** *(Balance Snapshots & Refunds)* |
| **28** | **Concurrent Over-Reservation (Hold Double-Spend)** | Multiple simultaneous hold requests attempt to reserve more funds than available in the wallet balance. | Parent snapshot row is locked `FOR UPDATE` in `ORDER BY ledger_account_id ASC`. Application and database trigger enforce $\sum \text{ACTIVE holds} + \text{newAmount} \le \text{postedBalance}$. Requests exceeding available funds fail with `InsufficientAvailableBalanceException` and roll back cleanly (0 hold rows created, unmutated balances). | **Phase 15** *(Balance Holds)* |
| **29** | **Hold vs. Spending Cross-Operation Race** | Client attempts to create a balance hold and execute a transfer/payment concurrently on the same funds. | All reservation and spending operations coordinate through deterministic `PESSIMISTIC_WRITE` locks on the wallet's `ledger_balance_snapshots` row. Both paths evaluate against `availableBalance = postedBalance - sum(ACTIVE holds)`. Mutual exclusion guarantees only one operation succeeds when combined funds exceed total balance. | **Phase 15** *(Balance Holds & Available-Balance Model)* |
| **30** | **Hold Expiration Race with Release / Consumption** | Scheduled background expiration worker attempts to expire a hold concurrently with an operation consuming or releasing it. | Multi-instance safe conditional update (`UPDATE ... WHERE id = :id AND status = 'ACTIVE'`) and trigger-enforced terminal status immutability guarantee exactly one terminal transition succeeds, preventing duplicate or contradictory lifecycle state changes. | **Phase 15** *(Hold Expiration & Lifecycle)* |
| **31** | **Balance Snapshot Corruption / Drift** | Hardware fault, direct DB tampering, or software bug causes `account_balances` to deviate from ledger sum. | Balance reconciliation detects the discrepancy; automated/manual repair recalculates the exact balance from immutable journal entries and corrects the snapshot. | **Phase 24 & 25** *(Reconciliation & Recovery)* |
| **32** | **Reconciliation Mismatch with PSP** | LedgerGuard records a transaction as `FAILED`, but PSP settlement report indicates `SUCCEEDED`. | Reconciliation engine flags a discrepancy item (`AMOUNT_MISMATCH` or `STATUS_MISMATCH`) and routes it to the `MANUAL_REVIEW` queue for operator intervention. | **Phase 24 & 25** *(Reconciliation Engine)* |
| **33** | **Business Failure Before Outbox Append (Scenario A)** | Financial validation fails or balance is insufficient during transfer/payment/refund before outbox event is appended. | The entire transaction rolls back cleanly in PostgreSQL; 0 business records, 0 journal transactions, 0 journal entries, 0 outbox event rows committed. | **Phase 16** *(Transactional Outbox Persistence)* |
| **34** | **Outbox Serialization or Persistence Failure (Scenario B)** | Outbox event payload serialization fails or database constraint on outbox table is violated during first execution. | The entire transaction rolls back via `Propagation.MANDATORY`; business state does NOT commit, no partial financial writes or unbacked transfers/payments exist, and idempotency slot is dropped for safe retry. | **Phase 16** *(Transactional Outbox Persistence)* |
| **35** | **Process Crash Post-DB Commit (Scenario C)** | Business operations, financial records, idempotency completion, and PENDING outbox event commit, but JVM process crashes before responding to HTTP client or publishing event. | All financial and outbox state remains durable in PostgreSQL. The PENDING outbox event represents undelivered intent and is safely picked up and published by the asynchronous publisher worker in Phase 17 upon recovery. | **Phase 16 & 17** *(Transactional Outbox Durability & Recovery)* |
| **36** | **Kafka Broker Send Failure / Unavailability** | Kafka cluster is temporarily unreachable or broker rejects send attempt. | `OutboxPublisherService` catches failure, throws `OutboxPublishException`, and rolls back the database transaction. Outbox row remains `PENDING` with `published_at = NULL`; subsequent scheduled publisher cycles retry automatically. | **Phase 17** *(Outbox Publisher Reliability)* |
| **37** | **Kafka Send Timeout / Ambiguous Outcome** | Broker ACK wait times out on `future.get(timeout)`; publisher cannot determine if message reached broker. | Publisher treats timeout as ambiguous, rolls back DB transaction leaving row `PENDING`. On subsequent retry, message is republished with the identical stable event ID (`outbox_events.id`), enabling idempotent deduplication at consumer inboxes. | **Phase 17 & 18** *(Ambiguous Delivery & Inbox Dedup)* |
| **38** | **Crash Post-Kafka ACK Before DB Commit** | Broker accepts message and sends ACK, but application process crashes or loses DB connectivity before committing `PUBLISHED` status. | Uncommitted DB changes roll back; outbox row remains `PENDING`. Upon restart, publisher worker repolls row and publishes it again with identical stable event ID, achieving safe at-least-once delivery. | **Phase 17 & 18** *(At-Least-Once Delivery & Idempotent Redelivery)* |
| **39** | **PSP Transport Failure Before Acceptance (`TEMPORARY_500`)** | External PSP returns HTTP 500 on first $N$ requests before accepting the transaction. | Deterministic fault injection produces HTTP 500 without creating provider operation or webhook rows (0 DB rows). Caller treats this as a known failure and can safely retry until success. | **Phase 19** *(PSP Simulator)* |
| **40** | **PSP Timeout After Success (`TIMEOUT_AFTER_SUCCESS`)** | Provider transaction commits successfully, but network delay/loss causes caller to timeout waiting for HTTP response. | Provider operation is committed as `SUCCEEDED` in the database *before* the delay occurs. Subsequent status lookup (`GET /api/provider/operations/by-client/{clientOperationId}`) confirms success; retry returns existing operation with 200 OK without re-executing. | **Phase 19 & 23** *(PSP Ambiguity & Status Recovery)* |
| **41** | **Delayed Webhook Delivery (`DELAYED_WEBHOOK`)** | Webhook callback is delayed in transit or queued for asynchronous delivery. | Operation succeeds immediately and returns 201 Created. Webhook is scheduled for `now + delayMs` and dispatched by background worker once due. | **Phase 19** *(PSP Simulator)* |
| **42** | **Duplicate Webhook Delivery (`DUPLICATE_WEBHOOK`)** | External network or provider delivers the same logical webhook callback multiple times. | Provider schedules 2 separate delivery rows carrying the exact same `eventId` and payload. Downstream receivers must use event ID deduplication to process side effects idempotently. | **Phase 19 & 22** *(Duplicate Webhook Delivery)* |
| **43** | **Webhook Target Endpoint Failure** | Downstream webhook callback URL is unreachable, times out, or returns HTTP 5xx. | Webhook dispatcher marks the delivery row as `FAILED` without failing or rolling back the `SUCCEEDED` provider operation. Financial and provider state remain authoritative. | **Phase 19** *(Webhook Decoupling)* |
| **44** | **Conflicting Provider Operation Replay** | Same `clientOperationId` is resubmitted with modified parameters (different amount, currency, or operation type). | Provider checks request fingerprint against existing record and rejects conflicting retry with HTTP 409 `Conflict`. Existing operation is not overwritten. | **Phase 19** *(Provider Idempotency)* |
